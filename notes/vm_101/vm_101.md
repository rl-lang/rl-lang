# VM 101

_before we start: This is a simplified conceptual walkthrough - `rl`-lang's bytecode VM differs in several ways_

## What is a Virtual Machine?

A VM is a simulated computer that executes instructions. Instead of compiling code to machine code for your specific CPU, you compile to bytecode for a fictional CPU (the VM), and then the VM interprets those instructions.

Think of it like a recipe:

```
LOAD 10
LOAD 20
ADD
STORE x
```

The VM reads each instruction, does what it says, and moves to the next one.

## How does it work?

The basic loop is:

```rust
fn run(chunk: &Chunk) {
    let mut ip = 0;  // instruction pointer
    let mut stack = Vec::new();

    loop {
        let opcode = chunk.code[ip];
        ip += 1;

        match opcode {
            OP_CONST => {
                let index = read_u16(&chunk.code, &mut ip);
                stack.push(chunk.constants[index]);
            }
            OP_ADD => {
                let b = stack.pop();
                let a = stack.pop();
                stack.push(a + b);
            }
            OP_SUB => {
                let b = stack.pop();
                let a = stack.pop();
                stack.push(a - b);
            }
            OP_RETURN => {
                let value = stack.pop();
                println!("{}", value);
                return;
            }
        }
    }
}
```

The stack is key - most instructions read from it and write to it.

## Stack-Based vs Register-Based

VMs come in two flavors:

**Stack-based** (like `rl`-lang):
```
LOAD 10     // stack: [10]
LOAD 20     // stack: [10, 20]
ADD         // stack: [30]
```

**Register-based** (like Lua):
```
LOAD r0, 10    // r0 = 10
LOAD r1, 20    // r1 = 20
ADD r2, r0, r1 // r2 = r0 + r1
```

Stack-based is simpler to implement but slightly slower (more instructions). Register-based is faster but more complex.

## Variables

Variables are just slots in an array:

```
// dec int x = 10
PUSH 10
STORE 0        // x is at slot 0

// dec int y = 20
PUSH 20
STORE 1        // y is at slot 1

// x + y
LOAD 0         // push x
LOAD 1         // push y
ADD            // stack: [30]
```

The compiler assigns slot numbers at compile time, so the VM doesn't need to do any string lookups.

## Control Flow

### If/Else

```
// if (x > 10) { ... } else { ... }
LOAD 0         // push x
PUSH 10        // push 10
GT             // x > 10? -> bool
JUMP_IF_FALSE else_label
  // then branch
  ...
  JUMP end_label
else_label:
  // else branch
  ...
end_label:
```

### While Loops

```
// while (x > 0) { x = x - 1 }
loop_start:
  LOAD 0        // push x
  PUSH 0        // push 0
  GT            // x > 0?
  JUMP_IF_FALSE loop_end
    // body
    LOAD 0      // push x
    PUSH 1      // push 1
    SUB         // x - 1
    STORE 0     // x = result
    JUMP loop_start
loop_end:
```

## Functions

When you call a function, you need to:
1. Push arguments onto the stack
2. Call the function (saves IP, creates new frame)
3. Execute the function body
4. Return the result
5. Restore the caller's frame

```
// push args
PUSH 10
PUSH 20
CALL 2         // call function with 2 args
// result is on top of stack
```

The VM maintains a **call stack** of frames, each with its own instruction pointer and local variables.

## Closures

Closures are functions that capture variables from their enclosing scope:

```rl
dec int x = 10
let f = || x + 1
println(f())  // 11
```

The VM needs to capture `x` when the closure is created, so it's available later even if the outer scope is gone.

## Compilation

Before execution, the AST is compiled to bytecode:

```
AST: Binary { left: Integer(10), op: Add, right: Integer(20) }

Bytecode:
  CONST 0      // index 0 in constant pool = 10
  CONST 1      // index 1 in constant pool = 20
  ADD
  RETURN
```

The compiler does one pass over the AST and emits linear bytecode. No optimization passes (yet).

## Why bytecode instead of tree walking?

| Approach | Speed | Complexity | Debuggability |
|----------|-------|------------|---------------|
| Tree walker | Slow | Simple | Easy (follows source structure) |
| Bytecode VM | Fast | Moderate | Moderate (need bytecode debugger) |

The bytecode VM is typically 10-100x faster than a tree walker because:
- No tree traversal overhead
- Instructions are just bytes, not heap-allocated nodes
- The dispatch loop is CPU-friendly
- The compiler can optimize before execution
